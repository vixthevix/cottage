more on the types
I will try to implement one more type, it will act kind 
of like a JSON. I think I will call it a COMPOSITE

think of it like a tree structure:
    LEAF NODES are the basic types listed above, including STRINGs.
    BRANCH NODES are these COMPOSITEs. 
    
    a COMPOSITE cannot be a LEAF NODE. 
    also, a COMPOSITE cannot be directly assessed; 
    you must instead access a LEAF NODE directly from it,
    or from its children COMPOSITEs.
    You will be able to do this using dot notation
    (e.g. studentInfo.name => STRING, 
    studentInfo.parentInfo.mother.age => UINT8)

In order for a COMPOSITE to work this way, almost always they
must be labelled as arrays. Otherwise, you just have a single
child node, which is kind of useless lmao

also, the void* data that a COMPOSITE takes is a siteVar.
So its like a multi-linked list lmao
I don't know how memory efficient it is, but for now make it work

actually, for the final implementation, it may be that the 
void* data of a composite, while still being of type siteVar*,
will act like a hashmap of siteVars.
In this way, you can access composite values 
normally (access),
by index (accessAt),
or by variable name (accessVar).

when initialised, will use a hash function using the name of the variable
to store into the thing.

and accessVar will also use the same technique

we will also need updateVar using hashing.
